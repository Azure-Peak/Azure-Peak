# Shadow's Preferences Menu™️v1.0

This folder controls the entire /datum/preferences UI.

## Overview

[ui_interaction.dm](ui_interaction.dm) has the primary TGUI configuration,
such as /ui_interaction, /ui_close, and /ui_state.

[preview_view.dm](preview_view.dm) has everything related to the ByondUi
element which displays a character preview.

[helpers.dm](helpers.dm) has a handful of helper procs that don't fit
anywhere else.

### [act](act/) and [data](data/)

These folders contains the /ui_act entry point at [\_act.dm](act/_act.dm),
and the /ui_data entry point at [\_data.dm](data/_data.dm),

In order to maintain mental reasoning around the highly complex and dense
functionality of the prefs menu, each of these procs are broken up
into trees of subprocs, which end up building the entire functionality of
the prefs menu together.

It's important to understand that most of this is "fake" and merely increases
mental separation, to make work on the prefs menu easier.

There is no "real" data segregation except at the
Tab (Character / Game Settings / Keybindings) level,
as DM is unaware of which subtab is being viewed.

For ui_data, at the boundary between DM and JS, every subproc's data is
flattened into a single linear list, save for deliberate structures
generated by the leaf nodes (last procs in the tree).

The same is true for ui_act, where behavior is built up by a tree of procs.
Currently, ui_act leaves are executed one by one in alphabetical order until
something returns non-zero. Accordingly, you should not expect to only receive
acts relevant to your proc! Every single action will traverse the whole ui_act
tree until it encounters something that returns TRUE upon seeing it.

There is room for optimization here, by mapping act names directly to
procs which handle it, but this has not proved necessary so far, as BYOND
executes 100 switch statements with no match quickly enough to not be
noticable. Be mindful though, refactoring this would break popup code!

## Code Style Rules

To make this approach work, it is critical to follow strict code style
and layout rules. Listed below are the general rules to follow to ensure
the prefs menu remains maintainable.

### Separate each Tab and Subtab into their own files OR folders.

Each TGUI Tab & Subtab should have exactly one act file and exactly one data file
handling every action it can take and every piece of data it needs accordingly.

As the UI grows, we need more and more nested modules to maintain separation
of concerns. Follow the same file layout as [Rust 2018 Modules](https://doc.rust-lang.org/reference/items/modules.html#module-source-filenames).

See the table below for an example:

| Hierarchy                                                                                                           | TGUI Path                                                                                                                                                               | Act Path                                                                   | Data Path                                                                    |
| ------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| Character Creator                                                                                                   | [tabs/CharacterCreator.tsx](/tgui/packages/tgui/interfaces/PreferencesMenu/tabs/CharacterCreator.tsx)                                                                   | [act/character_creator.dm](act/character_creator.dm)                       | [data/character_creator.dm](data/character_creator.dm)                       |
| Character Creator/Class                                                                                             | [tabs/CharacterCreator/subtabs/Class.tsx](/tgui/packages/tgui/interfaces/PreferencesMenu/tabs/CharacterCreator/subtabs/Class.tsx)                                       | [act/character_creator/class.dm](act/character_creator/class.dm)           | [data/character_creator/class.dm](data/character_creator/class.dm)           |
| [Character Creator/Appearance/FeatureChoice](## "This is a component that grew too big, and does not need DM code") | [tabs/CharacterCreator/subtabs/Appearance/FeatureChoice.tsx](/tgui/packages/tgui/interfaces/PreferencesMenu/tabs/CharacterCreator/subtabs/Appearance/FeatureChoice.tsx) | [act/character_creator/appearance.dm](act/character_creator/appearance.dm) | [data/character_creator/appearance.dm](data/character_creator/appearance.dm) |
| Game Settings                                                                                                       | [tabs/GamePreferences.tsx](/tgui/packages/tgui/interfaces/PreferencesMenu/tabs/GamePreferences.tsx)                                                                     | [act/game_settings.dm](act/game_settings.dm)                               | [data/game_settings.dm](data/game_settings.dm)                               |

If a piece of data or an action is required by multiple subtabs or tabs, lift
it up to the according index file, such as [data/character_creator.dm](data/character_creator.dm)
or [act.dm](act.dm).

Ideally you should put it in an existing proc such as `ui_data_character_creator_all_pages`.

### Maintain file-wise parity between Act, Data, and TGUI

In order to easily navigate between the UI code and the DM backend,
ensure that act, data, and TGUI files for each Subtab are named the same
thing.

Use snake_case for the DM files, and UpperCamelCase for the TGUI files.

For example, the Character Creator Tab has the Subtab [Class](/tgui/packages/tgui/interfaces/PreferencesMenu/tabs/CharacterCreator/subtabs/Class.tsx).
Accordingly, it is located in Class.tsx in the directory tabs/CharacterCreator/subtabs.

On the DM side, there is [data/character_creator/class.dm](data/character_creator/class.dm) and
[act/character_creator/class.dm](act/character_creator/class.dm).

### Name your Act and Data subprocs after their full hierarchy

In order to avoid any name conflicts, use the full hierarchy of a subproc
in their names.

For example, ui_act -> ui_act_for_tab -> ui_act_character_creator -> ui_act_character_creator_appearance -> ui_act_character_creator_appearance_body

These proc names are ugly and long, but predictable. Given that they are only
meant to be called by their parent in the tree anyways, this isn't a problem.

### Use the most specific type(s) possible for useBackend.

If your component only needs one specific piece of data, use the
smallest and most specific available data types to extract it.

For example, say we need the current slot ID and the character's real name. Instead of

```js
const { data } = useBackend<CharacterCreatorData>();
```

you should use

```js
const { data } = useBackend<CharacterSelectData & BasicCharacterData>();
```

This makes it clear to other developers what [data/](data/) files are being
used for a given component, rather than requiring them to track it down.

### Data procs should specify all possible keys in their initial var/list/data = list(), even when null.

This allows you to see at a glance what keys will be populated with this data proc.

#### Bad:

```js
var/list/data = list()
if(meow)
    data["meow"] = get_object()
else
    data["meow"] = null
```

#### Good:

```js
var/list/data = list(
    "meow" = null,
)

if(meow)
    data["meow"] = get_object()
```

### Use verbose_pref_log_x whenever you change something the user should know about!

There's two helpers that you should call whenever something changes the user
should know about, so that the changes are logged to the internal history_log
and printed to chat if they have `verbose_character_creator` enabled.

```dm
/datum/preferences/proc/verbose_pref_log_change(user, span, pref, before, after)
/datum/preferences/proc/verbose_pref_log_notification(user, span, message)
```

`span` can be `"notice"`, `"warning"`, or `"danger"` depending on whether or not
the change is potentially harmful/needs attention.

Examples of usage:

```dm
// Don't add quotes to before and after, it will automatically be "quoted".
verbose_pref_log_change(user, "notice", "Voice Pack", voice_pack_old, voice_pack_new);
// Do not include a period
verbose_pref_log_notification(user, "warning", 'Feature "[name]" colors reset');
```

## JSX/TSX rules

### Put attributes in alphabetical order (soft rule)

Unless otherwise stated below, just sort your attributes in vaguely alphabetical
order. If you think it looks better in some other order without violating the
rules below, go with that instead.

#### Bad:

```tsx
<Button tooltip={accessory.name} ellipsis fluid>
	{accessory.name}
</Button>
```

#### Good:

```tsx
<Button ellipsis fluid tooltip={accessory.name}>
	{accessory.name}
</Button>
```

### Large attributes should be towards the end of the attribute list.

If your attribute is multiple lines or significantly larger than any other
attribute, it should come as late as possible in the attributes list, save for
other longer attributes.

This rule is separated into two parts: Recommended order and Required Order.

#### Recommended Order

This is a recommendation for the section `[Everything Else]`: there are no hard
requirements here, use your best judgement for what appears visually balanced.

- Generally, sort alphabetically, within the sub-categories below.
- Short boolean attributes, ala `ellipsis`, `fluid`, `vertical`
- Short-to-medium text & variable attributes, ala `tooltip="Meow"`, `key={key}`
- `[Required Order]`

#### Required Order:

You **must** follow this order of every JSX element's attribute list.
Having these defined as a hard rule makes it more consistent across the UI, and
easier to read. If you find something out of this order, fix it!

- `key`: React keys must be the first attribute, always.
- `[Recommended Order]`
- WIDTH MUST BE BEFORE HEIGHT. We're working on a game for desktops with
  widescreen monitors, not phones!
- Object attributes such as `style={{ height: "200px", width: "100px" }}`
- JSX attributes such as `title={<Box fontSize={4}>Meow</Box>}`
- Function attributes such as `onEvent={() => { do_something(); }}`

#### Example: Bad

```tsx
<Section
	scrollable
	// breaks required order, JSX attribute is before a text attribute
	title={
		// height before width
		<Box className="fiveBuckTim" as="span" height={5} width={10}>
			Meow meow
		</Box>
	}
	className="PreferencesMenu__Section__NoChildPadding"
>
	<Stack zebra fill reverse>
		<Stack.Item minWidth={0} align="baseline" scrollable>
			<Button
				ellipsis
				// breaks required order, function attribute is before others
				onClick={() =>
					act("change_marking", {
						key: zone.zone,
						name: marking.key,
					})
				}
				fluid
				tooltip={marking.key}
			>
				{marking.key}
			</Button>
		</Stack.Item>
	</Stack>
</Section>
```

#### Example: Better (all Hard Requirements met)

```tsx
<Section
	// While alphabetic, too long, makes it easy to skip your eyes over scrollable
	className="PreferencesMenu__Section__NoChildPadding"
	scrollable
	// JSX Element Fixed
	title={
		// Width is now before Height, but still not alphabetized
		<Box className="fiveBuckTim" as="span" width={10} height={5}>
			Meow meow
		</Box>
	}
>
	{/* This is still out of alphabetical order */}
	<Stack zebra fill reverse>
		<Stack.Item minWidth={0} align="baseline" scrollable>
			<Button
				ellipsis
				tooltip={marking.key}
				// fluid should really be higher up!
				fluid
				// onClick is now following required order
				onClick={() =>
					act("change_marking", {
						key: zone.zone,
						name: marking.key,
					})
				}
			>
				{marking.key}
			</Button>
		</Stack.Item>
	</Stack>
</Section>
```

#### Example: Good (all Soft & Hard Requirements met)

```tsx
<Section
	// now in size & alphabetical & required order
	scrollable
	className="PreferencesMenu__Section__NoChildPadding"
	title={
		// Attributes were alphabetized (other than width x height)
		<Box as="span" className="fiveBuckTim" width={10} height={5}>
			Meow meow
		</Box>
	}
>
	{/* Attributes are now alphabetic */}
	<Stack fill reverse zebra>
		{/* Attributes are now alphabetic: minWidth is before scrollable */}
		{/* This is because they're almost the same width so alphabetical is better */}
		<Stack.Item align="baseline" minWidth={0} scrollable>
			<Button
				// Alphabetized & fluid is now closer to the top
				ellipsis
				fluid
				tooltip={marking.key}
				onClick={() =>
					act("change_marking", {
						key: zone.zone,
						name: marking.key,
					})
				}
			>
				{marking.key}
			</Button>
		</Stack.Item>
	</Stack>
</Section>
```

### Remember buttons grow, especially with user input! Don't let them overflow or resize your layouts!

This is a reminder that `<Button>` elements have a default `min-width: content`
_even when fluid_
and can grow a lot larger than your layout expects, especially if their text
is controlled by user input.

Tips for ensuring a button doesn't completely break your layout:

1. Consider entering as many `@` signs as you can, in any input that is later
   displayed on screen. This tends to reveal layout bugs as it's a
   very wide character in our default font.

2. Set `ellipsis` to make the button behave correctly when overflowing.
    - Without this, the button will happily render off the screen and look very weird.
    - When doing this, keep in mind the next rule!

3. Use minWidth={0} on their container when inside a Stack
    - This ensures that their container is allowed to shrink and shorten the buttons.

### Buttons that use `ellipsis` should always duplicate content to `tooltip`!

When you're using the `ellipsis` property to allow buttons to shrink, you are
also opting in to having the content no longer shown in full.

To ensure the user always knows what your button is supposed to say
even when it has overflowed, make sure the tooltip property is set.

#### Bad:

```tsx
<Button ellipsis fluid>
	{accessory.name}
</Button>
```

#### Good:

```tsx
<Button ellipsis fluid tooltip={accessory.name}>
	{accessory.name}
</Button>
```

## How to add new popups

1. Add a new `PREFERENCE_POPUP_` define in [code/__DEFINES/preferences.dm](/code/__DEFINES/preferences.dm)
2. Follow the pattern in [code/modules/client/character_setup/data/popup.dm](/code/modules/client/character_setup/data/popup.dm) and [code/modules/client/character_setup/act/popup.dm](/code/modules/client/character_setup/act/popup.dm)
3. Add your new component to [PreferencesMenu/popups/](/tgui/packages/tgui/interfaces/PreferencesMenu/popups/)

Follow this pattern:

```tsx
declare module "pm/popups" {
	interface PopupRegistry {
		CharacterSelect: "cs";
	}
}
registerPopup("CharacterSelect", "cs", PopupCharacterSelect);
```

4. Add a button somewhere that calls `setPopupId(PopupStateKey.YourNewKey)`

## Fixing previews in customizer selection

`/datum/sprite_accessory` does not support `get_icon_state` outside of an organ
context, so some things that depend on it may not initially work! To fix these
when they are noticed, simply specify `preview_states = list("a_valid_built_icon_state")`
on the `/datum/sprite_accessory`.

## Downstream Support

This UI has been built with downstream modifications in mind!
Ideally, downstreams will never have to manage a full unsynced clone of the
PreferencesMenu TGUI folder.

This is accomplished with two main concepts:

- Scattered around the code are comments starting with the text
  `INSTRUCTIONS FOR DOWNSTREAM`.
    - Use these comments to guide your modification of the system in a merge
      friendly manner.
    - If you find something you need to change that can't be done modularly,
      consider making a PR upstream to make it modular! For an example, look at
      how `/datum/preferences/proc/handle_title_pref_selection()` and it's call
      site work.
    - Also keep in mind that you can do something like the below example.
      This is a secondary option because it may require code duplication;
      use your best judgement for which option is more appropriate for a given
      situation.

```dm
// modular/override.dm
/datum/preferences/ui_act_character_creator(action, list/params, datum/tgui/ui, datum/ui_state/state)
    if(action == "existing_action_handled_elsewhere")
        return TRUE // control flow never reaches parent

    . = ..()
```

- The UI itself has a folder, [PreferencesMenu/downstream](/tgui/packages/tgui/interfaces/PreferencesMenu/downstream)
  which contain stub components that have been preplaced in ideal locations
  of the DOM tree to extend the UI in a way that blends in with original
  components.
    - This folder and files within should only be modified by upstream when
      there is a critical change to some core part of the prefs menu
      that requires downstreams to take action.
    - This space should be mostly safe from merge conflicts as a result, so
      downstreams should use these files to implement their custom logic.
    - Recommendation for downstream developers: Use
      `git checkout --ours tgui/interfaces/PreferencesMenu/downstream` when doing
      a merge that conflicts, and manually review what changes upstream has made
      to these files.
    - Pay attention to `INSTRUCTIONS FOR DOWNSTREAM` comments in the UI as well:
      not everything can be done with the downstream folder.
